# spotify

Imports Spotify data exports into Postgres and serves stats over GraphQL.

- `crates/export`: parsing of export files, shared by server and CLI
- `crates/server`: `spotify-server`, axum + async-graphql at `/v1/graphql`, a subgraph of graph.ortzi.cloud
- `crates/cli`: `spotify`, published as `ortzi spotify`
- `web`: React + Relay SPA (Vite, Tailwind), served by nginx in production
- `schema.graphql`: generated by `cargo test -p spotify-server`; the CLI's cynic types are checked
  against it. IDs are `spotify:<node>:<key>`, and every root field and type is prefixed `spotify`/`Spotify`
- `web/graph.graphql`: the graph router's public schema (`pnpm schema`), which the web app's Relay
  artifacts are checked against; production queries go through graph.ortzi.cloud for `node`

## Local development

```sh
docker compose up -d --wait db
export DATABASE_URL=postgres://postgres:test@localhost:5433/spotify

AUTH_DISABLED=true PUBLIC_URL=http://localhost:8000 cargo run -p spotify-server   # GraphiQL at http://localhost:8000/v1/graphql

export SPOTIFY_URL=http://localhost:8000
cargo run -p spotify-cli -- accounts add me
cargo run -p spotify-cli -- import "/Volumes/storage/spotify exports/2024" --account me
```

SQL uses the checked `sqlx::query!` macros, so building needs `DATABASE_URL` pointing at a
migrated database, or `SQLX_OFFLINE=true` to use the committed `.sqlx/` cache. After changing
a query or migration:

```sh
sqlx migrate run --source crates/server/migrations
cargo sqlx prepare --workspace -- --all-targets
```

`cargo test` needs `DATABASE_URL`; import tests create a throwaway database per test.

## Web

```sh
cd web
pnpm install
pnpm dev     # http://localhost:5173, proxies /v1/graphql to localhost:8000; login is skipped in dev
pnpm schema  # refresh graph.graphql once the supergraph has the server's schema changes
pnpm relay   # after changing a graphql`...` tag or graph.graphql; artifacts are committed
```

The image builds from the repository root: `docker build -f web/Dockerfile .`

Import each account's exports separately: `raw/` contains zips of both accounts' data.

## Deployment

Runs at https://spotify.ortzi.cloud (internal gateway), declared in
`~/Projects/k8s/projects/spotify/app.yaml`: Postgres, the `spotify` Kanidm public client, and
the API + SPA behind one route (`/v1/graphql`, `/health` → `spotify-api`; `/` → `spotify-web`).

- Pushes to `main` build `ghcr.io/accurate0/spotify` (server + CLI) and
  `ghcr.io/accurate0/spotify-web`, then `deploy-app-k8s-v2` bumps `image.values.yaml` in k8s.
- The API requires a Kanidm access token in the `spotify_users` group (`OIDC_ISSUER`,
  `OIDC_AUDIENCE`, `OIDC_GROUPS`; `AUTH_DISABLED=true` only for local development).
  `OIDC_PROVIDERS` (`<issuer>=<audience>,...`) trusts more than one Kanidm client, such as the
  `graph` federation router's, and replaces `OIDC_ISSUER`/`OIDC_AUDIENCE` when set.
- The CLI is published to the ortzi registry by `.forgejo/workflows/publish-cli-spotify.yaml`
  (bump `version` in `ortzi.yaml`); install with `ortzi install spotify`, then
  `ortzi spotify import <dir> --account <slug>`.

## Spotify Web API enrichment

`spotify-server enrich` fills in durations, release dates, credited artists, genres and
artwork (stored in the Garage bucket, served at `/art/...`; the API returns these as absolute
URLs under `PUBLIC_URL`, default `https://spotify.ortzi.cloud`), most-listened first. In
production it runs every 15 minutes as the `spotify-enrich` CronJob. The app is in Spotify's
Development Mode (one request per item, no batch endpoints), so it is deliberately slow:

- 4s between requests, at most 180 per run and 5,000 per rolling 24h
- a 429 with a long `Retry-After` pauses every run until then
- tracks Spotify no longer has are marked and never retried

```sh
spotify-server enrich --dry-run    # budget and the next items, no API calls
SPOTIFY_CLIENT_ID=… SPOTIFY_CLIENT_SECRET=… spotify-server enrich --max-requests-per-run 10
spotify enrichment                 # progress from the CLI
```

## Recently played

Exports arrive weeks after the plays, so `spotify-server recent` fills the gap from the Web
API's [recently played tracks](https://developer.spotify.com/documentation/web-api/reference/get-recently-played),
every 30 minutes as the `spotify-recent` CronJob. Each account links its Spotify user once:

```sh
ortzi spotify link me    # sign in as that account's Spotify user in the browser
ortzi spotify accounts list
```

The CLI catches Spotify's redirect on `http://127.0.0.1:8975/callback` (registered in the
Spotify app's redirect URIs; in Development Mode each Spotify user must also be added to the
app's users) and the API exchanges the code for a refresh token, stored in `spotify_links`.

- Spotify keeps only the last 50 plays, so polls must stay well under ~2.5h of listening apart.
- Plays land in `recent_plays` with the track (enriched from the response) but no play length,
  platform or reasons: `msPlayed` is null, and they pass the stats' minimum-length filter
  (Spotify only lists plays past 30s).
- `all_plays` hides them inside `extended_coverage`, like account-data plays, so when the next
  export is imported its plays take over the period it covers. Plays carry a `source`
  (`EXTENDED`, `BASIC` or `RECENT`), and `plays(sources: [...])` filters on it.
- A revoked authorisation marks the link (`revokedAt`) and polling skips it until linked again.
